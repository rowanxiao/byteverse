## 今日概览

截至今天 21:00（UTC+8），过去 48 小时的重量级消息集中在三件事上：英伟达董事会在黄仁勋辞任约十天后全票把他请回；智谱发布 GLM-5.4，第一次把「循环深度」做成旗舰模型的正式架构；Anthropic 让内部 Claude 模型证出 VP≠VNP，并连论文带 Lean 形式化一起公开。

- **[OpenAI 与 Cisco 开源 Shirudo：用 eBPF 给补丁窗口期打伞](https://openai.com/index/introducing-shirudo)**（OpenAI，11-23；[代码](https://github.com/shirudo-dev/shirudo)）

  Shirudo（日语「盾」）是一个开源的 Linux 运行时，做的事很具体：安全补丁从测试到全量部署往往要几天到几周，这段时间系统是裸露的；而漏洞利用和正常请求可能走同一批系统调用，直接封掉操作会让服务下线。Shirudo 用 eBPF 在运行中的内核里拦截有漏洞的代码路径，不重启、不改配置。

  公告里给的验证案例是：由 Codex 生成的盾牌给 Java 的 Base64 解码器加了输入检查，挂到运行中的 Elasticsearch 进程上，成功挡住 Java4Shell 的利用尝试而业务继续跑。工程细节值得看的是它把「可信」做成了流程——盾牌必须密码学签名才能加载，由内核 eBPF 验证器校验规则，加载与移除记录写进 TPM 供审计。BSD-2-Clause，免费，12 月 15 日有配套研讨会。这也是一个信号：模型厂商开始交付运行时组件，而不只是 API。

## AI 技术

- **[GLM-5.4：把 28 层循环两遍，用权重共享换推理深度](https://z.ai/blog/glm-5.4)**（智谱 Z.ai，11-23）

  这是智谱第一个基于 Loop Transformer 的旗舰模型：对 GLM-5 base 的 28 层做两次迭代，隐藏状态在第二次前向里被精修，参数量不变而有效深度翻倍，官方称达到 2T–3T 参数模型的水平。关键不是「循环」这个概念（2018 年的 Universal Transformer 就有），而是他们没从零预训练，而是在已预训练的 base 上继续训练改造，从而用较小的算力开销抬高上限。

  750B 规模下做了三处工程改动，都值得读：给每次迭代加独立的 per-token 门控，让第一遍保守写入、第二遍放开（激活范数不会炸）；混合 KV cache，第二遍复用第一遍选中的稀疏 KV、只额外保留一个滑动窗口，所以多一次循环只多一个窗口的缓存而不是整个上下文；稀疏注意力索引直接复用第一遍的结果。这些是「循环架构能不能便宜地部署」的核心。

  效果侧的数据：在 30B 同架构模型上做等参数对照，只多约 10% 训练算力就有明显增益，长链推理、数学、长上下文收益最大；多数基准上输出 token 反而减少 10–14%，等于把一部分思考从显式 token 挪进了隐式深度。推理速度闲时可达 200 tokens/s、峰值 70–80 tokens/s。限制也写明了：容易陷入超长的「马拉松式思考」循环，虽然这种反复自纠确实把准确率推过了同参数水平。API「即将开放」，权重计划在安全加固后开源。

- **[Anthropic 公开一份由 Claude 证出并形式化的结果：VP ≠ VNP](https://github.com/anthropics/formal-math/tree/main/vp-vnp)**（anthropics/formal-math，11-23 提交，北京时间 11-24 凌晨）

  结论是：对任意域，哈密顿回路多项式与特征不为 2 时的 permanent，其电路规模需要超过 m^(c(log m)^(1/3)) 个门（对所有足够大的 m 成立），近似电路同理，因此 VP 是 VNP 的真子集，VNP 不在 VP 闭包内。README 第一段就补了一句「这并不解决 P vs NP」——这点很重要，否则容易被二手转述放大。

  更值得注意的是生产方式：论文与 Lean 4 形式化「都由 AI 模型写成，没有人类数学家检查过证明」。仓库给了两级校验路径，`lake build` 加 `PrintAxioms` 确认除 propext、Classical.choice、Quot.sound 外没有别的公理；CI 里还跑 Comparator，用另一个独立编写的内核 nanoda 重查一遍。仓库明确标注「研究产物，不维护、不接受贡献」。

  对做工程的人，这条的价值在于流程示范而不是结论本身：LLM 产出 + 机器可检的证明 + 第二内核交叉校验，是目前唯一能在没有人类专家背书时给出可验证性的路径。同一天 HN 上还有人在做 agent swarm 攻 P vs NP，可以对照看「能生成」和「能被验证」差多远。

- **[Google：技术债务会让编码 agent「分心」，步骤多 70%、token 多 77%](https://www.infoq.cn/article/sFmubmDWkulIOTBLX0Dr)**（InfoQ 中文转述 Google 开发者博客，11-24；[原文](https://developers.googleblog.com/agent-distraction/)）

  Google 的两位工程师分析了数千名工程师的分布式追踪数据和数亿次 agent 操作，发现约 13% 的会话里 agent 会读到内联的 TODO/FIXME 引用，其中 6% 会真的对引用的缺陷采取行动——而多数情况下用户提示里根本没提这个缺陷。这些「绕道」里，41% 处理的是已经关闭的工单，57% 处理的是仍开放但超出请求范围的缺陷，也就是范围蔓延。

  代价用多向固定效应回归量化过：每次会话的步骤增加 70%、token 消耗增加 77%、等待时间增加 105%。他们的解法是写扫描 agent 去清理过时的 TODO——有些要翻好几年的 Git 历史才能确认引用确实失效——只在确认后才提 PR；过去 6 个月移除了数千条，人工审核认可率超过 95%。

  这条对正在给团队接编码 agent 的人最实用：上下文里的注释、文档、issue 引用都是 prompt 的一部分，清理技术债务从「代码卫生」变成了「模型准确率工程」。注意原文本次未能直接打开，数字与引述依据 InfoQ 中文稿，原始博客链接一并给出。

- **[Vercel AI Gateway 支持抽取模型：从文本、图片、PDF 里取结构化字段](https://vercel.com/changelog/ai-gateway-now-supports-extraction-models)**（Vercel Changelog，11-23）

  抽取（extraction）和生成是两种不同的调用约定：你给一段内容，要回的是若干独立字段而不是一段话。第一个上架的是 ScaleDown Extract-1，可从文本、图片、PDF 中抽出字符串或字符串列表，适合发票、合同这类记录，返回值带置信度。

  当前限制要说清楚：只能通过 AI SDK 用，需要 `ai@7.0.176` 及以上，API 是 `experimental_extract`，模型 ID 为 `scaledown/extract-1`。实验性 API 意味着接口可能变，但「模型直接返回带置信度的字段」这个形态，比自己拼 prompt + JSON schema 校验更省事，值得在票据类流程里试一次。

## 大前端与后端

- **[GitHub Issue 有了自己的状态，仓库看板进入公测](https://github.blog/changelog/2026-11-23-issue-statuses-and-repository-boards-are-in-public-preview/)**（GitHub Changelog，11-23）

  open/closed 二态确实不够用了，现在是七个状态：Backlog、Todo、In progress、In review、Done、Not planned、Duplicate，可在创建时选、也可在 issue 头部改，用 `status:` 过滤。

  真正影响工作流的是自动流转规则：关联草稿 PR → In progress；草稿标记 ready → In review；关联已开 PR → In review；分配给人 → Todo；**分配 agent → In progress**。最后这条说明 GitHub 已经把「agent 是 issue 的承担者」写进产品模型，而不是外挂。状态可通过 GraphQL、REST 和 MCP server 读写，也能作为 Copilot 自动化的触发器，和 Projects 里同名状态双向同步。

- **[PostgreSQL 19 正式发布：新增 REPACK，执行计划可以「给建议」](https://www.postgresql.org/docs/19/release-19.html)**（PostgreSQL 官方文档，11-19）

  发布时间 11-19，超出 48 小时窗口，但因为改动面大收进来。最实用的两个点：新的 `REPACK` 命令回收磁盘空间并重组表内容，`REPACK (CONCURRENTLY)` 允许不阻塞读写地做；`pg_plan_advice` 扩展让你干预查询规划器的决策，`pg_stash_advice` 则按查询自动套用这些建议——等于把「这条 SQL 必须走这个索引」从 hint 注释变成了可管理的对象。

  其他值得记的：逻辑复制在 `wal_level=replica` 下可以不开机重启就启用；序列值也能逻辑复制了；新增 `WAIT` 命令在 standby 上实现 read-your-writes 一致性；autovacuum 支持表索引并行处理，并引入评分系统决定优先级。升级前重点看 release notes 里的 Migration 一节。

- **[Cloudflare 把 DNS 探针接进 Flamingo：用 product 的 SLO 决定要不要回滚](https://blog.cloudflare.com/probing-dns-at-cloudflare/)**（Cloudflare Blog，11-23）

  起因是一次真实事故：发布 DNS 记录的服务出了调度 bug，服务本身健康、监控全绿，但部分记录变更几小时没发布出去，新主机名解析慢、证书签不出来。DNS 故障的特点就是慢、分散、局部——单测和仪表盘都看不见。

  做法是把 DNS 做成 Flamingo 的一个模块。Flamingo 是他们用 Rust 写的端到端测试框架，测试用自定义 DSL 描述（setup-request-assert），每天对边缘跑数亿次；把中间那步从「HTTP 请求」抽象成「动作」之后，加 DNS 查询就只是多一个 `Action::DnsQuery` 分支，调度、上报、资源管理全部复用。具体探针是持续更新一条带时间戳的 TXT 记录，从每个数据中心查三台权威 NS 和 1.1.1.1，断言权威侧 90 秒内、递归侧 600 秒内拿到新值。

  最后的闭环是 release gating：探针数据进 SLI/SLO，按 error budget 的燃烧速率判断这是长尾问题还是正在发生的事故，直接决定 promote 还是 rollback；如果某个 canary 机房传播延迟飙升，就在影响扩散前停掉这次发布。目前他们已经用同一套框架测 TCP、UDP、WebSocket。

- **[GPUI 从 Zed 仓库里独立出来](https://github.com/zed-industries/gpui)**（GitHub，11-23）

  GPUI 是 Zed 编辑器那套 GPU 加速的 Rust UI 框架，自述「同时结合 immediate 与 retained 两种模式」。现在它有了独立仓库、独立站点 gpui.rs 和 crates.io 上的包，HN 上讨论到 315 分。

  需要降温的是：README 现在只有一句「See you in a few weeks.」，没有任何文档、示例或版本说明，仓库也没有 license 文件。也就是说这是一个「宣布要拆分」的动作，不是可用版本。关注它的理由在于 Rust 桌面 UI 一直缺少一个被大规模生产验证过的框架，而 Zed 是少数真在天天用的样本。

- **[Vercel 给 ZDR 承诺加了主动探测：往 prompt 里埋一次性 canary URL](https://vercel.com/changelog/ai-gateway-now-runs-canary-zdr-audits)**（Vercel Changelog，11-23）

  这是 11-22 那起「推理供应商读取提示词」事件的直接后续。合同里的零数据留存（ZDR）条款和时点安全审计只能说明「供应商应该怎么处理数据」，但生产基础设施一直在变，所以需要一层检测。

  具体机制：每次审计为特定的 provider、模型、审计轮次铸一个独一无二的 URL，保证互联网上别处不存在；把带这个 URL 的 prompt 走正常推理链路发出去，同时把非 ZDR 的组合作为正对照一起发；然后盯着有没有任何请求打到这个 URL——ZDR 供应商不该保留、检查或爬取 prompt 内容，一旦出现请求，就能定位到具体是哪家、哪个模型、哪一轮。官方明确它补充而非替代合同与独立审计。
