## 今日概览

截至今天 10:30（UTC+8）。今天最值得看的是数学：同一天出现两份广义黎曼猜想（GRH）的证明——Levent Alpöge 自述与 Claude 合作完成、已在 Lean 中无假设形式化；Alessandro Masullo 的版本纯人类完成，经 Brian Conrad 数月审阅后仓促公开。Terence Tao 同时记录了 Alpöge 用 AI 做出来的另两份流体力学结果，并提醒「消化需要时间」。

安全与基建侧同周密集：OpenSSL 曝出 CVSS 9.8 的堆溢出，补丁 PR 还没合并；PostgreSQL 19 与 FFmpeg 9.1 在两天内先后发布，前者有一串默认值变更需要注意。

产品侧，Docker 把品牌定位改成「安全运行 agent」并给出沙箱策略 + MCP 治理 + 审计三件套；Vercel 把函数请求体上限从 4.5MB 提到 20MiB。

## 产品发布与更新

- **[Docker 把定位改成「安全运行 agent」，并给出治理三件套](https://www.docker.com/blog/agentic-ai-security-docker-governance/)**（Docker 博客，11-18；Product Hunt 今日榜第 3，11-20，212 票）

  产品叫 Docker AI Governance，答案分三层。沙箱策略管「能在哪跑」：基于 Docker Sandboxes 的 microVM，网络策略按域名/IP/端口放行，文件系统策略控制挂载点与读写权限，两者都在网络代理层与挂载层强制执行，不依赖 agent 遵守指令，可以用 `sbx policy check network api.anthropic.com` 在启动前检查边界。MCP 工具治理管「能做什么」：通过 MCP Gateway 用 Cedar 策略语言写规则，默认拒绝，可要求某类工具调用额外确认。审计管「看到了什么」：只记策略决策与会话事件的元数据，不含 prompt 与回复内容，可本地保存或转发到 SIEM。

  一个边界写得很清楚：MCP 策略只作用于经过 Gateway 的流量，如果 agent 在沙箱内直连远端 MCP server，就归沙箱网络策略管。

  对正在把 agent 放进生产流程的人，这套设计的价值是「权限边界可版本化、可 review」——改行为靠改策略，而不是指望模型下次听话。官方文章没有说明是 GA 还是预览，也没给价格，上线前需要去产品页确认。

- **[Currents：把 Playwright 的测试历史喂给 coding agent](https://www.producthunt.com/products/currents)**（Product Hunt 今日榜第 5，11-20，152 票）

  它是一个 2021 年就在做的 Playwright 测试面板，这次主打「给 agent 用」：新增 MCP server，让 agent 能查测试历史、flaky 比例与失败上下文；IDE 扩展让 agent 在编辑器里带着历史修失败；PR 检查能按测试结果阻塞合并。它还区分 flaky 与真实失败——这点对人重要，对 agent 更关键，否则 agent 会去追噪声。

  厂商自述的数字是 CI 时间最多降 50%、成本降 70%，来源是自家客户案例，不是独立评测。页面没列价格档位，需要去定价页确认。如果你的仓库已经有稳定的 Playwright 套件、又在用 agent 批量提 PR，这层「给 agent 的证据」是当前比较缺的；如果测试还没跑稳，先补测试收益更大。

- **[tensorViz：让 coding agent 看见 PyTorch 模型里真实的张量形状](https://www.producthunt.com/products/tensorviz)**（Product Hunt 今日榜第 10，11-20，95 票）

  做法很直接：跑一次真实的前向传播，把每个模块与张量形状变成可交互的图，Claude Code、Codex、Cursor 通过 MCP 查询这张图，读到的是实测形状而不是从源码猜的。它瞄准的失败模式很具体——agent 改一层，三个模块之后出现 shape mismatch，然后开始在猜测里打转。

  作者在评论区补充了两个限制：超大模型只能拿到局部图，但会按模块记录覆盖率，agent 能知道哪些部分缺失；图会随输入动态变化，不是只反映保存的那个样例。另外附了一个 560+ 篇近期论文模型的图浏览器，不用安装就能看。

  MIT 开源、免费，仓库在 [tensorviz-org/tensorviz](https://github.com/tensorviz-org/tensorviz)。做模型微调或推理服务的人值得装一次；纯前端项目用不上。

- **[Vercel Functions 请求体上限从 4.5MB 提到 20MiB](https://vercel.com/changelog/vercel-functions-now-support-request-bodies-up-to-20mib)**（Vercel Changelog，11-20）

  目前是 Public Beta，需要显式开启：设环境变量 `VERCEL_SUPPORT_LARGE_REQUEST_BODY=1`，且函数要使用 4GB 的内存档。生效范围是 Node.js、Python、Bun 运行时与 Routing Middleware；Edge 运行时仍是 4.5MB，超出直接返回 413，要吃到新额度得迁到 `runtime: 'nodejs'` 或 Next.js 的 `proxy.ts`。

  有一个容易踩的副作用：项目一旦开启，Routing Middleware 只收到请求头与元数据，拿不到 body——官方这样设计是为了避免 body 被传两遍、抬高成本与首字节时间。也就是说，靠 middleware 读 body 做签名校验或转发的逻辑会失效。

  4.5MB 这个限制此前逼着不少人绕过：图片直传、Webhook 中转、把大 JSON 拆包。20MiB 之后这些绕法可以收敛，但官方提醒要尽快读完 body、别长期驻留内存。

## AI 技术

- **[同一天两份广义黎曼猜想证明：一份出自 Claude，一份纯人类](https://terrytao.wordpress.com/2026/11/20/unforced-euler-singularity-unforced-navier-stokes-singularity-and-the-generalized-riemann-hypothesis/)**（Terence Tao 博客，11-20；当事人表述见 [Alpöge](https://simonwillison.net/2026/Nov/20/levent-alpoge/) 与 [Ravi Vakil](https://math216.wordpress.com/2026/11/20/hurried-announcement-alessandro-masullo-grh/)）

  Tao 按「消化程度」从高到低列了三件事：Alpöge、Buckmaster、Coiculescu 在大量 AI 协助下给出三维不可压缩 Euler 方程有限时间爆破的人类可读证明，并在 Lean 中形式化；Alpöge 与 Buckmaster 用同样方式做出 Navier-Stokes 的对应结果，Lean 化完成，但论文还需要专业重写；Alpöge 用「一个内部 AI 模型」生成了一份极长的、只有 Lean 代码的 GRH 证明。Alpöge 自己的说法是「与 Claude 合作」，两处表述不一致，照实并列。

  同一天还有另一条线：Ravi Vakil 宣布 Alessandro Masullo 的 GRH 证明草案，强调「全部由人类完成，没有 AI」，Brian Conrad 已审阅数月并给出大量反馈，本来打算再打磨一年，因为前者抢先公开而提前放出。

  关键限定词都在 Tao 那段里：GRH 那份是 Lean-only，验证与「提取证明策略」还在 Lean Zulip 上进行，他预计消化要花不少时间；Lean 编译通过不等于数学界接受，也不等于策略已被人类理解。对工程师的启发不在「AI 能做数学」，而在于可验证性成了区分「看起来对」与「确实对」的唯一基建——这套形式化流程，比结果本身更容易迁移到自己的领域。

- **[Inkling 2 Mini：26B 的循环 transformer，笔电能跑，专攻 agentic coding](https://thinkingmachines.ai/news/inkling-2-mini/)**（Thinking Machines，11-20）

  结构上的选择值得看：中间层对每个 token 跑三遍，用「多算几圈」换推理深度，从而少写 CoT。MoE 结构，26.4B 总参数、3.4B 激活、含循环后每 token 5.4B 权重激活；大部分权重以 NVFP4 训练并原生部署，最后四层 MXFP8，总内存约 20GB，能在 48GB 的 MacBook Pro 上离线跑（官方演示是在飞机上几分钟做出一个可玩的飞行模拟器）。

  在同规模开放权重模型里，它的 agentic coding 数字确实领先：DeepSWE v1.1 48.2%、SWE-bench Pro v2 Hard 77.9%、SWE-bench Verified 79.2%、Terminal Bench v4.0 5.6%。

  作者自己划的边界更有用：循环提升的是推理，不是知识——AA-Omniscience 上与同规模模型持平，SimpleQA 类知识密集基准不随循环次数提升；多轮聊天与多约束指令是弱项（MultiChallenge 50.0%、ComplexConstraints v1.1 33.4%，都低于 Qwen3.8-27B）。同时发布的可变循环研究模型还给出一个观察：循环加到十次，串行推理仍在涨，CoT 变短但保持可读，agentic sabotage 测试没有随循环升高。

  开放权重，Tinker 上可推理与定制。想在本机跑 agent 又不想为每次调用付费，这是目前少见的选项；但它不适合当通用聊天模型。

- **[模型可以改写自己的权重：无梯度、无训练，八次会话只升不降](https://arxiv.org/abs/2611.21885)**（arXiv 2611.21885，11-16 首发，11-18 修订）

  做法是让一个开放 27B 模型拿到自己的权重、自己的评分结果和运行自己的能力，诊断失败后直接改写对应的权重。作者称之为 self-rewriting，模型自己当优化器。效果分三条：在没见过的题目上提升 6.6 个点；每次改动先在练习题上验证、只提交有效的，连续八次会话准确率只升不降；还能修复一个被损坏到几乎全错的自身副本，在从不读取原始权重的前提下把图像任务恢复到原精度 80% 以上。

  与 test-time scaling 的区别写得清楚：收益写进了权重，因此每次回答没有额外成本；与训练的区别是它只跑前向传播，和推理一样。

  限制同样明确：只在一个模型家族上验证，且只有最大的那个能成功，小模型要么改不动要么把自己改坏；评测以图像任务与推理题为主，没有第三方复现。安全上这是个新问题——权重可以被模型自己改，审计与回滚要重新设计。

- **[Frostbite：AI 从零设计并验证的 CPU 架构，能效比 4.59 倍](https://architectlabs.com/blog/frostbite)**（Architect Labs，11-18）

  不是改现有的乱序核心，而是换了计算模型：基于交互网（interaction nets）的新 ISA，每一步都是局部的、依赖显式、每个值只有一个所有者，于是并行性来自程序本身，不需要线程、锁与中央调度器；没活干的瓦片从邻居偷任务，偷不到就休眠。「工作窃取」这个行为没有被人工指定，是 AI 在性能爬坡中撞出来的。

  数字：25 个工作负载上相对一颗现代双发射顺序核心，性能功耗比几何平均 4.59 倍（调优用的 10 个负载 6.02 倍，从未调优的 15 个留出负载 3.83 倍），面积性能比 8.77 倍；7nm 工艺，综合阶段 800MHz、最终 GDS 500MHz。AI 做了编译器、ISA、微架构、RTL、验证到 GDS，58 个想法留下 37 个；用自研规范语言 ASL 写「机器可检查的合同」，最终降级为 80 万行以上 Lean 覆盖 31 个模块，用来防奖励黑客。

  必须打折的地方：全部是硅前估算；对照 CPU 因法律原因不披露型号；FFT、排序、LU 等内核缩小了 64 倍；还没有操作系统，RTL 与 ISA 尚未公开。它的意义不在「AI 会做芯片」，而在 ASL 那层——把规格写成可机器检查的形式，才让 AI 的大规模产出可以被验收。

## 大前端与后端

- **[为什么 iOS 上至今没有非 WebKit 浏览器](https://blog.mozilla.org/en/mozilla/internet-policy/apple-ios-browser-engine-rules/)**（Mozilla 博客，11-20）

  DMA 生效两年多、日本类似规则落地近一年，Apple 确实在 EU 与日本开放了第三方引擎，但按 Mozilla 的说法，条件至今不可行：想用 Gecko 不能直接更新现有 Firefox，必须另建一个 App，然后让每个用户重新下载、迁移书签密码历史、手动切换。它的评价是「门开着，但更像翻板门」。

  Mozilla 提到一部分条件要求不披露项目的非公开信息，所以只能给这一个例子。它也没说清具体卡在哪几条——这既是对 Apple 的指控，也是谈判策略的一部分。

  对做 Web 的人，这条的实际含义是：iOS 上的浏览器差异不会因为法规而消失，Safari 的渲染与限制仍是唯一基准；跨端调试与兼容性预算得按「只有一个引擎」来算。

- **[GitHub CLI 新增 `gh event listen`，用一条命令等 PR 事件而不是轮询](https://github.blog/changelog/2026-11-19-wait-for-pull-request-events-with-github-cli)**（GitHub Changelog，11-19）

  需要 `gh` v2.105.0 以上。命令接收一个 PR URL 与关注的事件类型，创建订阅后打开事件流，把每个事件按 JSON 逐行打印；默认收到第一个事件就退出，适合塞进脚本；`--count` 等多个、`--follow` 持续监听、`--timeout` 设上限、`--jq` 提取字段。可监听的事件包括提交的 review、PR 状态与分支头变化、合并冲突、检查套件完成。

  更值得注意的是产品方向：`gh pr create`、`gh pr view`、`gh run view`、`gh run watch`、`gh api` 现在会主动提示改用 `gh event listen`，理由是 agent 场景下轮询既慢又浪费。

  当前是预览，需要加入 Event Streams 的等待名单，接口可能变。写 agent 的人可以先用它替掉 `while true; sleep 30` 那类循环。

- **[PostgreSQL 19 发布：REPACK 合并 VACUUM FULL 与 CLUSTER](https://www.postgresql.org/docs/release/19.0/)**（PostgreSQL 官方，11-19）

  头号特性是 `REPACK`，取代 `VACUUM FULL` 与 `CLUSTER` 两条老路，`REPACK (CONCURRENTLY)` 可以在不阻塞读写的情况下重整表，配套有 `pg_stat_progress_repack` 进度视图。计划器侧新增 `pg_plan_advice` 与 `pg_stash_advice`，可以按 query-id 固定或应用计划建议，这对「上线后计划忽然变差」是一把新工具。

  实际工程价值更高的几处：逻辑复制在 `wal_level = replica` 下无需重启即可开启，且支持序列值的逻辑复制；新增 `WAIT` 命令，让只读副本等到指定 LSN 被重放，实现读己之写（read-your-writes）一致性；autovacuum 支持索引并行清理并引入评分排序；TOAST 默认压缩从 pglz 换成 lz4。

  升级前必须看的破坏性变更：JIT 默认关闭（原来按代价启用被判定不可靠，分析型站点要手动打开）；`standard_conforming_strings` 强制为 on，旧版 `pg_dump` 且设为 off 的转储将无法载入；`inet`/`cidr` 的默认索引 opclass 从 btree_gist 改成 GiST，`pg_upgrade` 会拒绝含此类索引的集群；RADIUS 支持被整体移除；`max_locks_per_transaction` 默认从 64 提到 128。

- **[OpenSSL 曝 CVSS 9.8 堆溢出，修复 PR 尚未合并](https://github.com/openssl/openssl/pull/33652)**（OpenSSL PR #33652，11-10 提交、11-20 有更新；评分见 [GHSA-83xj-7xh4-4p7x](https://github.com/advisories/GHSA-83xj-7xh4-4p7x)）

  编号 CVE-2026-121481：当 `EVP_EncodeBlock()` 的输入长度接近 `INT_MAX` 时，编码后长度的计算会整数溢出，随后写越界，落到调用方提供的输出缓冲区之外（CWE-122 + CWE-190）。NVD 给的 CVSS 是 9.8，向量为网络可达、无需权限、无需交互。

  修复思路是把非法输入（NULL 缓冲区、负长度、编码后长度放不进 int）统一返回 `-1`，与 wolfSSL 的兼容层做法一致，并给 `EVP_DecodeBlock()` 加同样的保护、顺手修掉 `http_client.c` 里只判断 `len > INT_MAX` 的长度检查。

  现实约束要说清楚：GitHub Advisory 里受影响版本与修复版本都是 Unknown、状态是 Unreviewed；这个 PR 目前未合并。PR 作者给的利用路径是 `openssl s_client` 传极大的 `-proxy_pass`（须经环境变量传入以免命令行过长），配合接受大密码的 GOST 服务器。这个漏洞与 2021 年的 CVE-2021-23840 模式相同。在正式版本出来前，能做的是限制任何把外部长度直接喂给 Base64 编码的路径。

- **[FFmpeg 9.1「Gauss」发布](https://ffmpeg.org/download.html)**（FFmpeg 官方，11-20）

  9.1 分支于 10 月 24 日从 master 切出，20 日正式发布，库版本为 libavcodec 63.24、libavformat 63.16、libavfilter 12.8。变更集中在几块：LCEVC 的全链路支持（双轨处理、MPEG-TS muxing、payload 合并的 bitstream filter）、ASTC 图像编解码与 KTX 1.0 封装、通过 libfdk 的 xHE-AAC 编码，以及把 bitstream filtering 改成基于图的 API；硬件侧有 NVDEC CUARRAY 与 D3D12 DirectML 的零拷贝推理路径。

  对日常用 `ffmpeg` 命令行的人，更该留意的是移除项：`asf_o` demuxer 被删除。升级前先确认有没有脚本依赖它。

  媒体处理是 AI 应用里最容易被忽略的一环——上传、转码、抽帧、生成缩略图。这类大版本通常不需要立刻跟，但如果你的流水线卡在某个格式上，9.1 的 ASTC 与 LCEVC 值得看一眼。
