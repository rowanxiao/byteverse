## 今日概览

截至今天 09:50（UTC+8）。周末信息量偏小，但主线很清楚：形式化验证从"数学圈的玩具"变成了 AI 产出的验收流程——Lean 与 Mathlib 社区用一天时间独立核验了 Alpöge 的黎曼猜想证明，并逐条说明了凭什么相信它。

另一条线是钱。纳指上周五单日跌 5.28%，抹平 2026 年全部涨幅，Anthropic 上市第二天收跌 8.5%，主承销商关闭了护盘仓位。AI 资本开支的叙事第一次在龙头 IPO 之后被市场重新定价。

工程侧值得读的是 OpenAI 公开的 Codex 沙箱设计：默认权限怎么定、三套操作系统各自怎么落实、以及作者自己承认的一条逃逸路径。

## 行业动态

- **[Lean 与 Mathlib 社区认证黎曼猜想证明，四条标准逐条公开](https://leanprover-community.github.io/blog/posts/riemann-hypothesis/)**（Lean community blog，11-21；核验材料见 [MIT 汇总页](https://math.mit.edu/~drew/grh/)）

  11 月 20 日 Levent Alpöge 发布了一个约 1700 万行的 Lean 库，声称证明了黎曼猜想；次日 13:55，Lean 与 Mathlib 社区发布联合声明，确认四条标准全部满足：所证命题就是 Mathlib 里的 `RiemannHypothesis`（已由 Lean 与数论专家审过）、整个库可编译且多人复现同一份原始证明导出文件、用 comparator 与 con-leche --compare 两个独立工具比对确认命题一致、导出的证明被 Lean 官方内核与 con-leche、con-ron 等独立检查器验过。

  最后一条最关键：这些检查跑在一份"惰性"导出文件上，接触不到源文件里可能存在的恶意代码；con-leche 与 con-ron 自身还带一份相对于集合论的形式化证明，说明它们不会接受假证明。换句话说，这次不只是"AI 做出了数学"，而是第一次有一套可复现、可外包给陌生人的验收流程——评审成本从"读完证明"降到"跑检查器"。

  边界要说清：检查器只保证"证明与命题一致"，不判断命题是否有价值，也不替代同行对重要性的判断。另外，Hacker News 上的标题写作"广义黎曼猜想"，社区声明用的是 Mathlib 的 `RiemannHypothesis` 定义，两处口径不完全一致，正文以社区声明的链接为准。

- **[OpenAI 谈"对抗性蒸馏"：重点保护推理轨迹，而不只是拒绝输出](https://openai.com/index/combatting-adversarial-distillation)**（OpenAI，11-20）

  文章把蒸馏定义为安全问题而非单纯的条款问题：对手用前沿模型的输出训练另一个模型，再把它部署到没有同等防护的地方——比如蒸馏出网安能力，去做原模型会拒绝的事。OpenAI 的做法是对抗测试、训练、分类器、API 层防护，加上对协同提取行为的调查与封禁，并特别强调保护"受保护的推理轨迹"（chain-of-thought），因为中间步骤里有最终答案没写出来的信息，是最高质量的训练数据。

  它明确说 GPT-6.2 Astra 与 GPT-6.2 Sol 已加强这层防护。对做应用的人有两个现实影响：靠 API 输出做微调或评测的链路会更难走；如果产品依赖读取 CoT 字段做可观测性，需要准备字段被限制或脱敏的降级方案。文章没有给检测率与误伤率，属于厂商自述。

- **[联合国自主武器谈判未达成授权，规则真空延长到 2028 年](https://www.politico.eu/article/effort-regulate-killer-robots-delayed-until-2028-ai-un/)**（POLITICO Europe，11-21）

  128 个缔约国在日内瓦谈了一周，因需全体共识，俄罗斯整周用程序性手段阻挠，美国、英国、韩国、日本、土耳其、以色列等也反对有约束力的议定书。最终文件只写"在 2028 年前 elaborate 一份国际文书"，没有谈判授权，也没提法律约束力；成立政府间专家组，2028 年再报结论。

  人权观察与 Stop Killer Robots 的批评是可预期的，更值得注意的是巴西代表那句"不能只怪俄罗斯，有人躲在俄罗斯后面"。对做 AI 治理与合规的人，这条的实用含义是：短期内不要指望国际条约约束自主武器，能约束它的是出口管制、采购条款和本国刑法。

## 产品发布与更新

- **[Entire：把 PR 换成"评分轨迹"的 Git 托管平台](https://www.infoq.cn/article/6swrOq5xUXwVqrREwJwc)**（InfoQ 中文，11-21；[官网](https://entire.io)）

  创始人 Thomas Dohmke 是前 GitHub CEO，判断传统 PR 流程不适合多个 agent 高频迭代：时间线变成只有 agent 会读的审计日志。Entire 的做法是 trails——每次推送后，云沙箱里的评审 agent 给出置信度、风险、slop、测试覆盖等分数，界面置顶展示最近 5 轮结果，开发者按 gates 判断是继续让 agent 迭代还是合并；所有发现的问题必须解决或关闭才能合。配套的 continuous memory 把代码图谱、历史会话和 Git 记录存进仓库，供后续 agent 复用"为什么改"的上下文。底层是分布式 Git，官方宣称推送速度最高为 GitHub 的 89 倍。

  当前是 early access，按用量付费：注册送一次性额度，代码托管、trails、会话存储、记忆、CLI 免费，评审 agent 按模型厂商公开价格计费。需要权衡的是迁移成本与分数可信度——评估 agent 由你配置，分数好不好取决于你写的规则；89 倍是厂商自测基准。

- **[AI Context Flow 2.0：一份记忆走 MCP 同步给所有 agent](https://www.producthunt.com/products/ai-context-flow)**（Product Hunt 当日第 2，11-21，38 票）

  解决的问题很具体：同一个客户背景，在 Claude 里讲过一遍，换到 ChatGPT、Cursor、Grok 还要再讲一遍，十个工具十份半截记忆，还没有谁改过的记录。2.0 的核心是一个 MCP server：把记忆按项目或客户分 bucket，分别设访问权限，保留完整版本历史，agent 覆盖错了可以回滚；Memory Studio 提供集中查看与编辑。官方称已有 5000 多名用户。

  值得试的场景是同时用两三个 agent 干同一件事的人。限制也要看到：所谓"同一份记忆"取决于每个客户端是否老实走 MCP，而不是各自内置的记忆；榜单页只给了 7 天试用和年付 8 折码（AICFHUNT20，11-30 前），没有公开价格档位，试用前建议先确认按席位还是按 bucket 计费。

- **[Codemany：把 GitHub Actions 跑在自己已有的 Mac 和 Linux 上](https://www.producthunt.com/products/codemany)**（Product Hunt，11-21；[官网](https://codemany.com)）

  它不提供云 runner，而是编排你手头的机器：每台注册成 self-hosted runner，每个 job 起一个全新 runner 用完即弃，workflow 只改一行 `runs-on: [self-hosted, codemany]`。官方给出的私有仓库基准是平均快 3.0 倍（Hugo 从 2 分 16 秒到 31 秒，SwiftLint 从 14 分 27 秒到 3 分 33 秒），逻辑上说得通——本地机器没有冷启动和排队，缓存也在本地。

  14 天免费、不需要信用卡，之后 20 美元/月含两台机器。代价是机器、电费和维护都是你的；self-hosted runner 意味着仓库代码直接在你机器上执行，隔离与清理得自己兜住，别把生产凭证留在那台机器上。

- **[gitroots：给 GitHub 加路径级权限，人和 agent 同一套审批](https://www.producthunt.com/products/gitroots)**（Product Hunt，11-21，9 票）

  场景来自外包团队：想让某个人只改一个模块，结果不得不把整个仓库给他。gitroots 在 GitHub 之上做一层治理：按人、团队或 agent 设定可访问路径，读写权限分开（可以读共享类型、只能在指定目录写），越界改动变成待审批的同步请求，网页、手机或 CLI 都能批，读操作也进审计。Claude Code、Codex 走的是和人一样的检查。

  Starter 免费，付费 19 美元/月起，目前只支持 GitHub。作者在评论区自己承认了一个重要限制：同步进目标仓库的提交不再保留原作者的 Verified 签名，而是记在 gitroots ops 名下，身份与审批链只在 gitroots 内部可追溯——对要求签名可验证的团队，这是硬伤。

## AI 技术

- **[OpenAI 公开 Codex 沙箱：默认能写工作区、能读全盘、不能联网](https://openai.com/index/inside-the-codex-sandbox)**（OpenAI Engineering，11-18）

  这是这几天最值得读的 agent 工程文。Codex 用 permission profile 描述文件系统与网络边界，内置的 `:workspace` 默认值是：工作区内可写，但 `.git` 与 `.codex` 只读（防止改 Git hooks 和配置）；文件读取放开到整个磁盘（受操作系统原有权限约束），因为编译器、SDK、依赖都在仓库外；网络默认关闭，需要时按域名放行，流量走沙箱外的代理，靠 `*_PROXY` 环境变量注入。执行层面 macOS 用 Seatbelt（SBPL 策略），Linux 用隔离命名空间加代理中继，Windows 正在迁移到微软新出的 MXC（Microsoft eXecution Container）库。

  可复用的部分在最后：`codex sandbox` 命令能把同样的边界套到你自己的工具上，文章还给了"给 MCP server 套沙箱"的例子——这对自建 agent 的人比产品本身更有价值。

  作者没有回避漏洞：往 `node_modules/prettier` 注入恶意代码，`git status` 看不到，编辑器保存时就在沙箱外执行了。结论是沙箱只是纵深防御的一层，对齐训练和权限设计不能省。

- **[形式化验证成了"反 slop"的生意：cvc5 作者谈 veri-coding](https://latent.space/p/formal-verification)**（Latent Space，11-20）

  Clark Barrett 是 SMT 求解器 cvc5 的联合创造者，现在是 &Truth 的联合创始人。他给了一个干净的定义区分：agent 跑测试、自我批评、让另一个模型打分，这些工具都能找到很多问题，但你永远不知道"是不是还剩一个"；形式化验证回答的是"什么时候算完"。cvc5 在 Amazon 的 agent 开发环境 Kiro 里用于规约分析和测试生成，他称生产管线每天调用数十亿次。

  &Truth 的思路是在 Lean 上搭"验证机器"：先做开源 C 代码的地图（&Atlas），目标是读任意语言的代码、证明它满足精确写下的需求。文章同时提到 Anthropic 用 Lean 形式化了费马大定理（约 1300 万行），以及 GPT-6.2 Astra 产出 Smoktunowicz 间隙定理的 Lean 证明。

  限制在前提里：需求得先写成形式规约，这步仍然靠人；这是一篇访谈加厂商介绍，没有独立评测，别把"能验证"当成"已普及"。

- **[LookAtMyQuant：把 Inkling-2-Mini 压到 5.4 GB，并给出每档的掉分曲线](https://github.com/ShinMegamiBoson/lookatmyquant)**（GitHub，11-21 上榜）

  做法不是拍脑袋选量化格式，而是逐块测量"压缩这一块会让输出偏多少"（KL），再在体积预算内给每块分配码本：trellis codes、按 Fisher 信息分行分配位宽、最后用 4000 步蒸馏把每层重压一遍。作者把同一套配方用到三个模型上，数字都摆在同一张表里。

  以 Inkling-2-Mini（26.4B 物理参数、5.4B 激活的循环 MoE）为例：12.76 GB 版在 GSM8K、HumanEval 和 4 项视觉测试上与 BF16 教师完全一致（349/349）；8.87 GB 保留 98.9%；5.38 GB 版掉到 GSM8K 88%、HumanEval 70.7%。在 M5 Max 上，12.8 GB 版 prefill 2,016 tok/s、串行解码 60.5 tok/s，配 4-bit drafter 后中位 112.7 tok/s。

  限制写得也算老实：只在 Apple Silicon 的 MLX 运行时验证；基准的逐题结果与 dense 权重没有发布；5.4 GB 那档"能跑"但代码能力明显退化，选档位不能只看体积。仓库还有一份用三条命令跑通 SmolLM2-360M 的教程，适合当量化入门的实操材料。

## 大前端与后端

- **[WebKit 放出 spatial CSS 开发者预览：用 CSS 组织 3D 场景](https://webkit.org/blog/18621/introducing-spatial-css-a-developer-preview/)**（WebKit Blog，11-16）

  visionOS 27.3 的 Safari 提供了 spatial CSS 的第一批组件。`spatial: portal` 让一个容器成为共享空间，里面所有子元素共用同一套坐标；子元素继续用标准 `transform` 摆放，`position-anchor` 把模型吸附到锚点，`@environment-map` 管理不同光照环境，`portal-action: orbit` 让用户绕场景旋转，`requestVolumetricScene()` 启动 volumetric 场景。`<model>` 元素本身已在 Safari 27 全平台可用。

  设计取向值得注意：3D 内容不写 JS 状态机，而是复用媒体查询、过渡和动画这套已有机制——同一份页面在手机、桌面和头显上按能力自适应。目前要在 visionOS 的 feature flag（CSS Portals）里手动打开，属提案预览，别当稳定 API 用。

- **[Raph Levien：下一个 100 个 Rust GUI 的建议](https://linebender.org/blog/next-100-guis/)**（Linebender Blog，11-21）

  四年前那篇"下一个十几个 Rust GUI"之后，又冒出约 20 个工具包，但真正上生产的旗舰只有 Zed（自研 GPUI）。作者观察到的新变量是 AI：LLM 写 Rust 的成本并不比 TypeScript、Kotlin、Swift 高多少，而类型系统在大型代码库里更利于维持不变量，所以 Rust 正在成为"AI 重写既有代码库"的目标语言——Discord 的重写就选了 GPUI。

  他也不吹：GPUI 的 2D 渲染器适合文本编辑器，缺渐变、混合、滤镜，不是通用渲染器；Rust + UI 双精通的工程师仍然难找。这是从业者的判断而非基准测试，但"AI 把语言迁移成本拉平后，选型会重新看安全与性能"这个推论，值得放进技术选型的讨论里。

- **[Muru：mod_wsgi 作者用 Rust 重写 Python 应用服务器](https://simonwillison.net/2026/Nov/21/muru/)**（Simon Willison，11-21；[代码](https://github.com/muruhq/muru)）

  Graham Dumpleton 二十年前写了 mod_wsgi，现在用 Rust 做了 Muru，目标是把开发和生产放在同一个进程模型里：import once / fork many、开发期自带 HTTPS、按 worker 上报的指标伸缩、缩到零、不重启即可发布、不用 service mesh 做金丝雀、在容器里当更好的多租户租客、与 Kubernetes 协作而不是绕开它，最后是每页一个 toolbar 和 trace 面板。他从 11 月 4 日起把每一步设计都写成了公开记录，18 篇连着看是一条完整的工程叙事。

  他自己在那篇"AI as a lifestyle choice"里说得很直白：表面上 AI 干了很多活，但"什么还不够好"仍由他判断，二十年踩坑的经验正好用在这上面。项目还早，没有生产采用案例，但 Python 部署层十几年没大变化，这套把开发体验和运维放进同一设计的思路值得跟。

- **[gopgext：用 Go 写 PostgreSQL 扩展，TinyGo 生成 C 胶水](https://jespino.github.io/gopgext/)**（项目文档，11-21 上榜）

  写普通 Go 文件，用 `//gopgext:function` 标注，工具自动生成 C glue、安装脚本和控制文件；标准库可用（fmt、regexp、encoding/json、crypto、泛型、defer/recover），类型映射到 SQL；除函数外还能写触发器、聚合、GiST/GIN/SP-GiST/BRIN 操作符类、FDW 和查询钩子。移植自 contrib 的 pgcrypto、hstore、pg_stat_statements、cube 都能通过上游回归测试。

  作者在首页用黑体写着 experimental：不要上生产。原因很实在——生成代码或 Go runtime 的 bug 跑在数据库进程里，能崩库、能坏数据，API 与生成的 SQL 也随时可能变。适合本地做原型或内部工具，不适合承载业务数据。

- **[GPGME 修一个可导致 RCE 的 double free（CVE-2026-129975）](https://lists.gnupg.org/pipermail/gnupg-announce/2026q4/000517.html)**（GnuPG 安全公告，11-20）

  根因在读取 gpg 状态行与密钥列表的两个内部函数：缓冲区扩容后，新指针只在函数末尾写回 context，一旦因读错误提前返回，context 仍指向已释放的内存，最终 double free。用一把带超长 user ID 的 OpenPGP 密钥即可触发，可被用来从应用里外泄数据，公告称不能排除进一步做成 RCE，建议立即升级到 GPGME 2.3.1。

  影响面比想象大：Gpg4win、GnuPG Desktop、多数邮件客户端和不少 XMPP 客户端都链接了 GPGME。原定 11 月 25 日协调披露，因 ruby2shell 事件，GitLab 提前动作，这个洞也就在 11-20 一起公开了。如果你维护的桌面应用集成了 GPG，先查依赖版本，再确认发行版是否已回填补丁。

- **[Upload2Shell：Ghostscript 字体加载器越狱，波及 WordPress、Roundcube、CUPS](https://pwn.ai/upload2shell)**（pwn.ai 研究，11-21 起公开案例）

  Type 1 字体加载器的 use-after-free（CVE-2026-125396）可以越过 Ghostscript 的 `-dSAFER` 沙箱、改掉原生的路径控制并执行命令。真正麻烦的是攻击面：任何"上传后渲染"的链路都可能把文件送进 Ghostscript——WordPress core（Author 及以上，或被授予 upload_files 的 Contributor）、Roundcube 查看邮件时缩略图附件、Plesk Obsidian、Debian 13 的 CUPS（未认证的 IPP 打印任务以 lp 身份执行）、MediaWiki 的 PdfHandler、DokuWiki，以及走 ImageMagick delegate 的一堆服务。

  修复其实早已发出：Ghostscript 10.08.0（9 月 8 日）、Ubuntu USN-8949-1、Debian 13 安全更新，WordPress 另有 CVE-2026-65640；CVE 编号 11 月 9 日分配，本次是公开案例研究陆续上线。工程上的结论不只"升级"：把渲染器当不可信代码跑——独立容器、断网、只读挂载、限制文件类型白名单，比只校验扩展名有用得多。
