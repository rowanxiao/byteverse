- **[Java4Shell：OpenJDK 的 Base64 解码越界写，CVSS 4.0 给到 9.2，默认配置可未授权 RCE](https://calif.io/java4shell/)**（Calif，11-17；补丁版见 [Aikido 汇总](https://www.aikido.dev/blog/java-17-rce-vulnerability-cve-2026-114938)）

  问题出在 HotSpot 的 x86-64 Base64 intrinsic：为了快，它用 AVX-512 VBMI 的 `evmovdqub` 一次写 64 字节，写多少由掩码决定。处理带 padding 的尾部时，代码先把输出长度减一，遇到 `=` 这种边界情况会算成负数，掩码变成全 1，于是 64 字节全写。输入 64 个 `A` 加一个 `=`（JDK 17 上是 128 个 `A` 加 `=`）时，解码器只分配了 50 字节的数组，实际从偏移 48 开始写 64 字节，越界 62 字节。Java 随后会拒绝这个输入并抛 `IllegalArgumentException`，但内存已经脏了。

  作者用远程堆布局（heap feng shui）把这个常量覆写做成了堆泄露加 RCE，并在默认配置下打通了 Keycloak、Atlassian Jira、Atlassian Confluence、JFrog Artifactory、Jenkins、PingFederate 的未授权路径，以及 Kafka、Solr、Elasticsearch、Gerrit、Spinnaker 的登录后路径；Struts 与 Spring Boot 的示例应用也复现了。samczsun 还提供了一个客户端方向的利用：一个 Java 程序主动连向恶意 TLS 服务器，即使自己不开端口也会中招。

  影响面：OpenJDK 17.0.6 及以后，含 Corretto、Temurin、Microsoft Build of OpenJDK、Zulu、Liberica、SapMachine、Red Hat 与 Oracle 各发行版；硬件上要求支持 AVX-512 VBMI 的 x86-64（Intel Ice Lake 起、AMD Zen 4 起），ARM64 不受影响。Oracle 在美国时间 17 日 13:00 PT 发布修复版，对应 17.0.21.1、21.0.13.1、25.0.5.1、27.0.1.1，Corretto 侧为 17.0.21.1.2 等；Temurin 当时尚无确认修复版。临时缓解是启动参数 `-XX:-UseBASE64Intrinsics` 或 `-XX:UseAVX=2`（后者只加在 x86-64 主机上，ARM 上会启动失败）。

  ```bash
  grep -m1 '^flags' /proc/cpuinfo | tr ' ' '\n' | grep -E '^(avx512f|avx512bw|avx512vbmi|bmi2)$'
  ```

  四个 flag 全出现才算硬件在范围内。截至 17 日，Aikido 表示尚未见到在野利用——这类洞的关键就在这几天，容器基础镜像和随应用打包的 JDK 是最容易被漏掉的地方。

- **[eve 1.0：Vercel 的代理框架转为正式版，中位单轮延迟从 3.036 秒降到 414 毫秒](https://vercel.com/blog/eve-is-now-generally-available)**（Vercel 博客，11-17）

- **[Claude Code 团队怎么做验证：90% 的代码由 Claude 写，靠什么才敢放行](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)**（claude.dev，Addy Osmani，11-16）

  这篇是目前少见的、把「代理产出如何验证」写到操作层的材料。前提数字：团队约 90% 的代码由 Claude 编写与评审；在结构化文件生成的内部测试里，另设一个评分者按 rubric 检查 Claude 的产出，任务成功率最多提升 10 个百分点，越难的任务收益越大。

  值得抄的几条：验证等于把改动跑起来，他们在仓库里放一个 `verify` skill（`.claude/skills/`），用 Chrome 扩展、iOS/Android MCP、computer use 或本地起服务做端到端冒烟，这一步比单元测试更重要；失败三轮就停下交给人；代码所有者写自己的检查，检查触发时要说明理由；可靠性清单 39 条，每条都有可从 diff 读出的触发条件，Claude 只查命中的 3 到 10 条；一个 reviewer 多轮，而不是叠第二个更贵的 reviewer，`REVIEW.md` 从基础分支读，保证「改动不能修改审判自己的规则」；每次提交盖上「如何验证」的戳，包含「none」，并有 off / observe / enforce 三档提交门禁，连续被拦两次后下一个放行，免得 Claude 卡死。

  测试本身的纪律也很硬：flaky 测试不许跳过、不许加 sleep、不许重试到通过，找不到根因就删掉并记录原因。对正在把代理塞进 CI 的人，这份清单可以直接当模板。

- **[lend：把凭证留在笔记本上，让远端代理隔着 SSH agent 请你批准执行](https://blog.antonio.cx/running-agents-with-lend)**（antonio 的博客，11-13；Hacker News 11-17 讨论）

  作者把代理跑在一次性 VM 上，笔记本留着 SSH 私钥、1Password 库和已登录的 `gh` 与云 CLI。常规两种做法他都不满意：把 token 拷到 VM，机器上任何进程都能读到且在有效期内一直有效；用 `ssh -A` 转发 agent，则 VM 能用全部密钥且没有签名记录。

  lend 是一个挡在 SSH agent 前面的代理，你转发它的 socket 而不是真的 agent。VM 上代理请求执行 `gh` 时，请求经 socket 回到笔记本，`gh` 在笔记本上以你的身份运行，通过 MCP 暴露成单个工具 `run_local_command`，且 reason 必填。策略默认全拒，规则可精确到可执行文件路径与 `args_prefix`，审批方式是弹窗里直接按 Touch ID（`biometric:inline`）。密钥可以按指纹白名单、限制 `max_signatures`；租约（5 分钟或 3 次）只在会话内有效，锁屏即失效；需要 token 的命令用 `op read` 在本地注入环境变量，值不进提示也不进历史。

  作者也写清了它不防什么：批准的命令以你的用户身份运行，lend 不做沙箱；批准 `env`、`sh` 或解释器等于把一切交出去；提示里的调用方信息来自 VM 可以被伪造。目前支持 macOS 与 Linux，不分配 PTY，交互式程序跑不了。这类「能力留在本地、远端只拿结果」的模式，很可能成为代理基础设施的默认形状。
