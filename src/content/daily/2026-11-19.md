## 今日概览

- **[nginx 两个 HTTP/2 内存破坏漏洞，官方发布 1.30.7 与 1.31.9](https://nginx.org/en/security_advisories.html)**（nginx 官方安全公告，11-18；技术细节见 [Wiz 研究](https://www.wiz.io/blog/nginx-http2-rce-vulnerabilities)）

  CVE-2026-123007 是 HTTP/2 流控的整数下溢。流被取消时，未发送数据的窗口额度被「退回」，退回时没有检查上限，计数器溢出成极大值；这个值一路传到 `ngx_ssl_send_chain()`，有符号与无符号转换后变成越界内存拷贝。影响 1.9.5 到 1.31.8，开了 HTTP/2 就成立，官方定级 major。

  CVE-2026-123633 是 HTTP/2 连接的 use-after-free。只发半个 HEADERS 帧时连接被标记为可复用，补完帧、请求开始处理后却没有把它从可复用链表里摘掉，影响 1.19.7 起，官方只定级 medium。

  Wiz 的评级更重：两个洞 CVSS 4.0 都是 9.2，且在官方 1.31.7 / 1.31.8 构建上做出了带 ASLR 绕过的未授权 RCE；123007 甚至不需要后端应用，一台只发静态文件的 HTTPS 服务器就够。分歧的原因在利用条件——需要 64 位、HTTP/2 over TLS，还要堆布局，CDN 与 WAF 若能终止 HTTP/2 会挡掉一部分回放。

  处理方式很直接：升到 1.30.7（stable）或 1.31.9（mainline），Plus 对应 37.0.7.1 / 37.0.8.1。升不了就在 `server` 块写 `http2 off;`，并从 `listen` 指令里去掉 `http2` 参数，重载后确认旧 worker 已退出。同一批还修了 HTTP/3 的 UAF（CVE-2026-121810）与 resolver 的 UAF（CVE-2026-123634），同属 9.2 分档。

  ```nginx
  # 临时缓解：关闭 HTTP/2，并从 listen 中移除 http2 参数
  server {
      listen 443 ssl;
      http2 off;
  }
  ```

- **[Gemini 4 Neon：$3/$15 的前沿档，100 万上下文](https://blog.google/innovation-and-ai/models-and-research/gemini-models/introducing-gemini-4-neon/)**（Google，11-18）

- **[Cloudflare 开放 Clairic 与 Clairic-flash 权重：27B / 9B 的专用抽取模型](https://blog.cloudflare.com/open-clairic/)**（Cloudflare 博客，11-18）

  这两个模型只做一件事：把非结构化内容抽成结构化字段。27B 的 Clairic 这次重写架构——文本与数字字段改成并行槽位自回归生成，每个字段按已写内容选下一个 token、到自己的结束符就停，所有字段在同一个 batch 里推进；另外训练了专门的头处理估算、预测、时长、日期推算与算术。9B 的 flash 是压缩版，延迟更低。

  价格按输入 token 计：Clairic $0.24、flash $0.10（每百万），12 月 1 日前两者都按 $0.10 促销。延迟是它真正的卖点，官方自测 p50 从 155 毫秒到 691 毫秒，取决于任务。图片与 PDF 现在都能读，一次最多 4 张图或 4 页；返回仍带置信度与字符 span，方便做校验。

  权重在 Hugging Face 上以 open-weight 放出，Workers AI 端点是 `@cf/cloudflare/clairic` 与 `@cf/cloudflare/clairic-flash`。注意评测全是自测，官方也写明没有公开的抽取基准，与 Liquid D1.2、Scaledown Extract 的对比只能当方向参考。

- **[Energy-Based Reasoners：1.8M 参数、99.9% 数独准确率，推理算力少 345 倍](https://energy-based-reasoners.github.io/)**（论文项目页，11-18 上 HN；[论文](https://arxiv.org/abs/2611.08977)、[代码](https://github.com/wwillchen/ebr)）

  做法是把循环推理当成能量函数上的梯度下降：能量低表示当前推理状态与输入更相容，梯度给下一步方向，梯度足够小就停。这一套同时解决三件事——不需要外部验证器就能给候选打分、简单题自动早停、多候选取能量最低者。

  数字：模型只有 1.8M 参数，Sudoku-Extreme 上 99.9% 准确率（5 次采样），比次优的 EqR 少用 345 倍 FLOPs；N-Queens 8×8 单次通过率 100%；多解任务用 5 次采样就超过别人 128 次采样的结果。作者来自 Duke、UIUC 与 Harvard，代码已开源。

  限制要说清：四个基准全是合成算法题（数独、迷宫、N 皇后、图着色），没有自然语言或开放域任务；模型只有百万级，向大模型迁移未经验证；停止阈值需要调。它证明的是「小模型加好的停止判据」在特定任务上极省算力，不是通用推理的替代方案。

- **[22 种 harness × 5 个模型：换模型时，外壳也要重选](https://runta.com/blog/introducing-frontierharness-eval-v1-1/)**（Runta，11-17；[看板](https://frontierharness.org/)）

  规模够大：27,280 次运行、83B token，22 种 harness 配置 × 5 个模型（GLM-5.3、GLM Flash、DeepSeek、Muse、Kimi-K3）× 62 个终端任务 × 4 次尝试，全部用默认设置。

  第一条结论：同一模型下最贵与最便宜的 harness 相差 1.8～5.0 倍成本，但贵不等于准——5 个模型里有 4 个，最贵 harness 的通过率反而低于最便宜的；换模型时 harness 的中位排名会移动 11/22 位。方差分解显示每任务成本 92.8% 来自模型、2.3% 来自 harness、4.9% 来自「模型 × harness」配对，也就是说 harness 的差异有一大半要看它配的是谁。

  第二条：钱主要花在失败上。64.5% 的标价成本落在没通过的试验里，其中 68%～82% 的失败是给出错误答案而非超时；prompt 大小、工具数量、缓存命中率与每通过成本几乎无关，步骤数才是主因（秩相关 0.51），因为每一步都要重发整个上下文。要给代理省成本，先压步骤数，而不是抠 prompt。

## 大前端与后端

- **[gh CLI 2.105.0：用事件流等 PR 变化，不再轮询](https://github.blog/changelog/2026-11-18-wait-for-pull-request-events-with-github-cli)**（GitHub Changelog，11-18）

  `gh event listen <PR 链接> --events review_submitted` 会订阅该 PR、打开事件流，每个事件输出一行 JSON，默认收到第一个事件就退出，也支持 `--count`、`--follow`、`--timeout`、`--jq`。可监听已提交的 review、状态变化、head 变更、合并冲突、check suite 完成。

  预览阶段，依赖同样是预览的 GitHub Event Streams，需要先进等待名单。`gh pr create`、`gh pr view`、`gh run view` 等命令现在会主动建议用事件流代替轮询——对把代理挂在 CI 或笔记本上等结果的场景，这能把「每 30 秒查一次」换成「睡着等推送」，顺带省掉限流额度。

- **[Alloy CSS：一份样式表，关掉 JavaScript 也能用的 dialog、menu、tabs](https://alloyhtml.com/)**（Alloy CSS 官网，11-17 上 HN）

  它只针对服务端渲染出来的 HTML：dialog 就是一个 `<dialog>` 加一个指向它的按钮，menu 用 popover，排序、开关、toast 靠原生行为，因此没有脚本可加载、可损坏、可维护。暗色模式是再链一份主题样式表，跟着 `prefers-color-scheme` 走。

  真正有意思的是它对着 AI 写的定位：把类名清单交给模型（站点提供 `llms.txt`），并用 `npx @alloyhtml/css check` 抓模型编造的类名——示例里 AI 按 Bootstrap/Tailwind 习惯写出 `.mt-4`、`.btn-primary`，检查器直接报这三个类不存在。还有 `npx @alloyhtml/css skill` 把规则装进 Claude Code 项目。

  适合当「无构建、无框架的小后台或文档站」的起点，也是一种约束式设计：类名少，AI 乱编的空间就小。复杂交互仍要自己写脚本，它不打算覆盖。

- **[Speed Insights 默认测量 soft navigation，SPA 的路由切换也能算 Core Web Vitals](https://vercel.com/changelog/speed-insights-now-measures-soft-navigations)**（Vercel Changelog，11-17）

  以前只统计整页加载，单页应用里点一次路由跳转的 LCP、CLS、INP 全在盲区。现在默认开启 soft navigation 测量，客户端路由变化按同样的指标上报。

  对做 SPA 的人，价值是数据终于对齐真实体验：首屏好看、切页卡顿的站点，以前在报表里是「优」。代价是基线会变，切换当周的历史对比要看清楚口径。

- **[单秒静态部署开始支持 CSS、图片与字体等资源](https://vercel.com/changelog/single-second-static-deployments-now-support-more-assets)**（Vercel Changelog，11-18）

  之前「跳过构建、直接秒级上线」只适用于纯 HTML，现在带静态资源的站点也能走这条路，条件是符合条件的站点通过 CLI 或 API 部署。含义是这类站点不再占用构建机时间，CI 里「改一行文案也要跑一遍完整构建」的流程可以省掉。

  对本站这种纯静态站点是直接可用的路径，但要注意它假定资源没有经过构建期转换。
