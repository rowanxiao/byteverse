## 今日概览

截至今天 11:30（UTC+8）。今天最值得读的是 OpenAI 首席科学家 Jakub Pachocki 的一篇长文：他把 AI 进展归结为「压缩器」训练的持续推进，首次公开内部的预训练困惑度数据，并主张用这个指标给全行业画一条「共同上限」——这是少见的、把安全标准建立在可量化曲线上的提议，同时也等于公开了自己的位置。

与之配套的另一条来自 OpenAI：反蒸馏（adversarial distillation）防御的技术细节与执法数据，把「从早前请求中提取受保护推理」的攻击成功率从 54.0% 压到 0.2%，并承认每周有数千到数万个账号被处置。

工程侧，今天有三条可以直接拿来用的东西：一个把「慢的 5%」用编码 agent 移植到 Rust 并逐调用验证的工具，一个用 MCTS 给编码 agent 加分支搜索的实验，以及 GPGME 的一个需要立刻升级的双重释放漏洞。

## 行业动态

- **[OpenAI 披露反蒸馏执法规模：每周数千到数万账号，推理提取成功率降到 0.2%](https://openai.com/index/combatting-adversarial-distillation)**（OpenAI，11-20）

  所谓对抗性蒸馏，是不良行为者用前沿模型的输出训练一个能力接近的模型，然后在不带同等防护的情况下部署——能力迁走了，护栏没跟上。OpenAI 给出的两层防御是：请求级（对模型做对抗训练让它拒绝披露受保护推理、输入与输出分类器连工具调用参数一起查、API 侧把受保护推理与产生它的对话历史绑定，早期消息被改写就丢弃后续推理），以及 campaign 级（调查账户网络、跨供应商共享入侵指标、配合 consistent-standards 政策）。

  数字很硬：在六个攻击模型的自适应黑盒评估里，「从早前请求提取受保护推理」的攻击成功率从 GPT-6 Astra 的 54.0% 降到 GPT-6.2 Astra 的 0.2%，从当前请求提取从 22.9% 降到 0.9%。另一组 teacher→student 实验说明保护精确推理轨迹确实能限制网络能力迁移，脚注提到 Anthropic 在 SWE-bench Verified 上有类似结论。执法侧，今年每周处置规模从数千到数万账号，夏季明显上升；文中重申 9 月把一起活动核心归因于与 Moonshot AI 相关的个人、2 月就 DeepSeek 疑似蒸馏向国会做过简报——这些都是 OpenAI 单方表述。

  对做 Agent 的人，这篇的可取之处不是结论而是清单：把受保护推理绑到对话历史上、查工具参数里的泄漏、把攻击日志留成回归测试。它也明说了未解决的部分：能力到底能迁走多少还在研究，白盒攻击会比黑盒测试更严峻。

- **[一份案例研究估算：Anthropic 2028 年 87% 电力来自天然气、11% 来自煤](https://betterdatacenterproject.com/2026/11/16/how-ai-is-powered-a-breakdown-of-byop-and-grid-power/)**（Better Data Center Project，11-16；HN 讨论 11-22）

  报告用「自带电源（BYOP）」加电网边际机组的方式估算单个公司的用电结构：截至 2026 年 10 月 Anthropic 已签约 15 GW 算力，其中 5.9–9.6 GW 落到具体站点，按此推算 2028 年约 87% 来自天然气、11% 来自煤，中位情形排放 3200 万吨二氧化碳当量，报告还提到该公司近期以 34 亿美元买下 1.7 GW 重型燃气机组的承诺。

  这是外部机构的建模估算而非公司披露，方法论与假设都可以在原文里查；同一份报告也给了一个更大的背景数字：全美已规划的 BYOP 天然气容量 177 GW。对开发者的意义在于成本曲线的另一面——推理价格里除了芯片与电力，还压着越来越难拿的并网许可与排放约束，长期合同的定价逻辑会跟着变。这条的发布时间是 11-16，因 HN 昨日才把它推上来而收进今天。

- **[Backblaze 更新隐私政策，客户担心备份数据被共享](https://www.backblaze.com/company/policy/privacy)**（Backblaze 政策页，11-22；[背景报道](https://www.neowin.net/news/backblaze-customers-worried-of-personal-data-salesharing-after-policy-update/)）

  值得试的理由是「个人上下文」这件事现在被反复提起，但多数方案要求你把资料上传到某个服务。它的代价是 39 美元买断、只支持苹果生态、iCloud 同步是可选项——跨设备不同步就完全没有云端副本，这既是隐私优势也是可靠性风险。

- **[Vercel CLI 加了一条给 agent 用的命令：用一句话描述任务来找命令](https://vercel.com/changelog/agents-can-now-find-vercel-cli-commands-by-describing-the-task)**（Vercel Changelog，11-19）

  `vercel help search "roll back production" --with-help` 会返回匹配的命令列表，加 `--with-help` 顺带把第一条的帮助页一起给出，agent 不必猜参数。更实用的是它认识 API 端点：匹配到某个 API 时返回一条填好路径与必填占位符的 `vercel api` 命令；`--json` 输出结构化结果；对「show」代替「list」这类措辞和轻微拼写错误也做了容错。CLI 里还附了一个 skill，提示编码 agent 先走这条搜索，Vercel 声明不记录搜索文本。

  这是「给 agent 设计的 CLI」里比较克制的做法：不新增一堆子命令，而是把已有的命令树变成可检索的目录。如果你在给自己的工具做 agent 接口，这个模式值得抄——尤其是返回占位符而不是让模型自由拼路径这一点。

- **[Vercel Functions 请求体上限从 4.5 MB 提到 20 MiB（公测）](https://vercel.com/changelog/vercel-functions-now-support-request-bodies-up-to-20mib)**（Vercel Changelog，11-20）

  需要设置 `VERCEL_SUPPORT_LARGE_REQUEST_BODY=1` 手动开启，按环境生效，所以可以先在 preview 上试；同时要求函数使用 4GB 的内存档位。生效范围是 Node.js、Python、Bun 运行时和 Routing Middleware，Edge 运行时仍是 4.5 MB、超限直接 413——想用大请求体就得把 Edge 换成 `runtime: 'nodejs'` 或 Next.js 的 `proxy.ts`。

  有一个容易被忽略的副作用：项目一旦开启，Routing Middleware 只能拿到请求头与元数据、拿不到 body，这是为了避免同一个请求体被发两遍、抬高成本与首字节时间。也就是说，依赖在 middleware 里读 body 做校验或签名的实现会失效，迁移前先 grep 一遍。

- **[LangSmith Tool Gateway 公测：把 agent 的工具调用收进一层带审计的网关](https://www.langchain.com/blog/langsmith-tool-gateway)**（LangChain 博客，11-19）

  它要解决的是 agent 从「聊天框」走向「按计划或事件自己跑」之后的问题：每个 agent 能调哪些工具、以谁的身份调、调用记录在哪。Tool Gateway 托管工具凭据与身份，按策略限制可用工具，把每次调用写进 trace；和已有的 LLM Gateway 并排，前者管模型调用与花费，后者管工具调用与访问。官方把需求拆成三件事——访问（能用哪些工具、用哪份凭据）、控制（每个用户能做什么、必要时走审批）、可见（谁调了什么、凭据对不对）。

  公测阶段可直接在 LangSmith 里接 MCP server；deny 策略与审计日志需要联系销售。这里的分歧点值得留意：把工具治理交给平台，等于把 agent 的身份体系也交给平台，和自建 OAuth 相比是控制权与工作量的交换。

## AI 技术

- **[OpenAI 首席科学家公开预训练困惑度数据，主张用它设定行业「共同上限」](https://openai.com/index/perplexity-and-intelligence)**（OpenAI，11-22）

  Jakub Pachocki 的论证链条是：现代 AI 的本质是训练一个压缩器，困惑度（等价于交叉熵损失）就是压缩进度的度量。文中给出的一条曲线大致是——GPT-3.5 约 0.99（流畅对话，催生初代 ChatGPT）、GPT-4 约 0.91（开始有效使用思维链），低于 0.8 后进入网络安全、数学等「变革性能力」区间，0.76 附近开始产出数学开放问题的突破；作者预计 0.68–0.70 会出现下一轮跃迁，而具体是什么形态目前连测试都没有。

  真正的动作是后半段：OpenAI 公开了内部预训练的困惑度数据（等于让对手看清自己的位置），并提出「共同上限」——各前沿实验室共同承诺，在达到某个具体的能力里程碑（例如 CoT 监控器的后继者）之前不越过按这类指标划的红线。作者也列了困惑度的四条局限：跨实验室因数据集不同难以直接比较、与可操作评估脱节、反映不了预训练之外的进展（CoT 不降困惑度但显著提升能力）、存在未知下限且越接近下限进展越慢。

  对做应用的人，这篇最有用的是那句自陈：AI 参与「预训练算法研究」可能带来阶跃，最快 2027 年。若真如此，今天围绕上下文长度、检索质量、工具编排做的工程优化会面临一次假设重置——不是失效，而是它们要服务的模型能力基线会移动。

- **[SimpleBench 更新榜单：OpenAI 的 6.2 系列反而退步，社区在争这是不是「递归深度」的代价](https://simple-bench.com/)**（HN 讨论，11-21，182 分；榜单数据据讨论转述）

  SimpleBench 用 200 多道需要常识与时空推理的多选题考模型，人类非专家基线 83.7%（9 人小样本），官方页面称目前最强模型 Claude Fable 为 81.9%。这次更新后，按 HN 讨论里的转述，Anthropic 的 Fable 5.2 升到第一、5.1 第七，而 OpenAI 的 Astra 6 排第九、Astra 6.2 掉到第十五，Sol 6.1 第十、6.2 掉到第三十。

  讨论里的两种解释都没有定论：一种认为 6.2 为了效率与成本牺牲了这类「反套路」推理，另一种猜与递归深度一类的架构选择有关；也有人指出题目本身就是「无关细节 + 一个隐含常识」的固定套路，模型学会了按经典谜题作答反而出错。需要提醒的是，榜单是 JS 渲染的，我这次只读到官方的方法说明与人类基线，名次变化来自评论转述，未经逐条核实——把它当「某个基准上出现了可讨论的退化」看，而不是「模型变差了」。

- **[agent-mcts：给编码 agent 套一层蒙特卡洛树搜索，用生成测试当裁判](https://github.com/natsu0529/agent-mcts)**（GitHub，11-21）

  生产环境里的编码 agent 基本是单条线性循环：执行、观察、原地重试，没有分支也没有回退。这个项目用一个薄适配层驱动 agent 的无头模式（`claude -p` 已验证，Codex 适配器只对假二进制测过），把每次尝试挂到搜索树上，让失败的分支回溯、把预算压到看起来最有希望的路径上。

  作者公开的基准很小但很诚实：两个有明确规格的任务（npm semver 范围、ISO 8601 时长），每种设置 20 次运行，答案由 agent 看不到的隐藏测试打分。只靠可见测试搜索几乎等于单次运行（19/20 无变化）；加一个读 diff 的判官平均 +5.4 分但成本涨到 1.81 美元；先生成测试再搜索最好——16/20 变好、2/20 变差，平均 +4.8 分、耗时约 19 分钟、每次 2.44 美元。作者自己点破了边界：收益主要来自「失败的测试告诉下一次改什么」，在只有一段模糊 bug 报告的任务上，测试写错就会把正确修复判成失败（v0.4.0 有 10/10 次返回未修复代码）。三个任务、一个模型，不能当普遍结论。

- **[LangChain：给 agent 建一座「知识工厂」，而不是继续加长 context](https://www.langchain.com/blog/knowledge-factory)**（LangChain 博客，11-21）

  Harrison Chase 把问题重新定义了一遍：缺的不是更强的模型，也不是更多 context，而是可复用的知识。他把要维护的东西分成三类——技能（公司内部「正确做法」的流程与脚本，过去只在同事之间口口相传）、领域知识（人、产品、竞品、组织的事实与政策，不易过时）、数据访问指引（数据在哪、该查哪个源、怎么查）。第三类最容易被做错：如果数仓里已经有唯一可信来源，就不该再复制一份，需要维护的是「去哪查」。

  工厂的三个部件更实用：给 agent 一个「报告缺失/错误知识」的工具；一个按节奏在后台跑的 curator agent，它能读原始来源（Notion、Slack）、能读 agent trace、也能读前面的举报，负责更新与去重；以及知识的存储与版本。作者明确反对让干活的 agent 自己维护知识——它们各有目标，写出来的东西会互相矛盾。

- **[一份家用本地模型指南：装 Unsloth、按显存挑量化版本、开 LAN 访问](https://www.gpupartner.com/blog/beginners-guide-local-ai-inkling-qwen-unsloth)**（GPU Partner 博客，11-22，HN 307 分）

  作者想解决的是「token 限额 + 隐私 + 价格」三件事叠加后的疲劳：把耗 token 的调研、数据整理、编码任务放到自己机器上。流程被压到很短——装 Unsloth Desktop、下载一个能塞进显存的量化模型、设上下文长度、打开 LAN 访问让全家用；硬件是一张 32 GB 显存的 RTX 5090，装好之后 10–15 分钟能跑起来（不含下载）。

  这是一篇个人实践记录，不是基准测试：没有吞吐、首 token 延迟、长上下文衰减的数据，样本也只有一套硬件。它的价值在于把「本地跑一个够用的模型」的成本降到可试的程度——如果你只是想把一部分重复劳动从 API 账单里挪走，先按显存挑模型比先比分数更实际。

## 大前端与后端

- **[Simon Willison 做了一页 select 样式标本：三条 CSS 就能让下拉框在各浏览器长得一样](https://simonwillison.net/2026/Nov/22/select-styling/)**（Simon Willison，11-22）

  他嫌 `<select>` 默认样式在各浏览器差异太大（尤其 Chrome 里不好看），于是让模型生成了一页「把 select 能改的样式全列出来」的标本页，再逐项截图对比桌面与移动端。最终他常用的写法是 `appearance: none` 重置原生外观，配 `padding`、`border`、`border-radius`，箭头用内联 SVG data URI 作 `background` 放在右侧，这样一个规则就能在三种浏览器里对齐。

  这类内容的实用之处在于它承认了浏览器差异是常态：与其等平台统一，不如把重置 + 自绘箭头做成一个稳定的小组件。要注意的是 `appearance: none` 会连带去掉部分平台的可访问性提示（例如某些触控设备的下拉手势样式），上线前仍需在真机上过一遍。

- **[Linebender：给接下来 100 个 Rust GUI 的建议](https://linebender.org/blog/next-100-guis/)**（Linebender 博客，11-21）

  Raph Levien 四年半后再写这个题目。观察有三条：自上次以来新出现了约 20 个 Rust GUI 工具包，AI 又把兴趣推高了一轮；真正在用 Rust 写 UI 的旗舰应用仍然很少，最知名的是基于自研 GPUI 的 Zed，而 GPUI 正成为「AI 驱动的重写」里的热门选择，比如 Discord；GPUI 适合编辑器场景，但渲染层缺完整渐变、混合与滤镜，还不到 Vello/Skia 那一档。

  他的核心判断是采用慢的两个原因正在消解：写 Rust 比 TypeScript/Kotlin/Swift 难、懂 Rust 又懂 UI 的人少；但有证据表明 LLM 写 Rust 的成本并不比其他语言高多少，而类型系统在大代码库里更利于守住不变量。这个论证对前端出身的人有直接含义——如果你在评估「客户端要不要重写」，语言成本这一项正在被重新定价，剩下的是生态与招人。

- **[fast-anything：别整体重写成 Rust，只重写最慢的那 5%，并用真实调用逐条验证](https://github.com/EL4CTEO/fast-anything)**（GitHub，11-22，HN 181 分）

  思路是把「重写」缩小到函数级：`scan` 先剖析应用、按耗时与可移植性给函数排序；`port` 录制最多 500 次真实调用，生成只含一个函数的 Rust crate 和一份给编码 agent 的任务说明；`verify` 用 release 构建回放全部录制调用，再补上 NaN、±∞、-0.0、非 ASCII、空输入与放大 16 倍的输入等边界用例；全部通过且不比原实现慢，才允许 `enable`，而且切换是「一个被标记的代码块」，可以逐字节还原。浮点按 1e-9 容差比对，原始实现出错的地方移植版也必须出错。

  作者举的反例很有说服力：一个「看起来对」的移植比较了字节而不是字符，500 次真实调用里有 148 次把它抓了出来。支持 Python、Node、TypeScript、Ruby、Java、Kotlin、Go、PHP、C/C++、C#、R，MIT 许可，同时也做成 Claude Code 插件与 MCP server。边界是它假设热点集中——如果瓶颈分散在 I/O 与序列化，这条路省不下多少。

- **[gopgext：用 Go 写 PostgreSQL 扩展](https://jespino.github.io/gopgext/)**（项目文档，11-21，HN 167 分）

  目标是把 PostgreSQL 扩展的开发语言从 C 换成 Go，覆盖的范围相当宽：SQL 函数与自定义类型、FDW、GiST/GIN/SP-GiST/BRIN 索引访问方法、自定义扫描与聚合、选择率估算、hook、认证、共享内存、触发器、全文检索、表采样，外加一个 `http` 框架层。文档给了安装、教程、命令行与 API 参考。

  项目自己标了 experimental，这决定了它现在的定位：适合做内部工具、验证想法，或者在 C 扩展的构建成本太高时试一条替代路径。真正的风险不在 API 而在运行时——Go 的 GC 与 goroutine 调度嵌进 Postgres 的进程模型，长期稳定性需要自己压测，别在不了解失败模式的情况下上生产主库。

- **[GPGME 修一个双重释放漏洞，可导致数据外泄，RCE 未排除](https://lists.gnupg.org/pipermail/gnupg-announce/2026q4/000517.html)**（gnupg-announce，11-20）

  CVE-2026-129975：用一个用户 ID 极长的 OpenPGP 密钥就能触发双重释放，攻击者可借此从应用里窃取数据（例如通过发送签名数据），官方明确写「不能排除被利用来做远程代码执行」，建议立即升级。根因很具体：GPGME 读 gpg 状态行与密钥列表的两个内部函数先分配 1024 字节缓冲，需要时扩容，但新指针只在函数末尾才写回上下文；如果中途因读取错误提前返回，上下文仍指向已被释放的旧指针，最终二次释放——中间的其它分配还可能让分配器的常规双重释放检查失效。

  影响面包括 GPGME 2.3.1 之前的全部版本，以及基于它的 Gpg4win、GnuPG Desktop、GnuPG VS-Desktop。时间线也值得记：GitLab 于 11-12 通知，原定 11-25 协同披露，因 Ruby2Shell 需要提前，GPGME 也在 11-20 一并公开——也就是说这个洞是在没有任何缓冲期的情况下被推到台前的，依赖它的桌面与邮件客户端应当按「已在被利用」的假设处理。

- **[FastAPI 0.165.0：表单解析加上可配置上限，并给编码 agent 配了官方 skill](https://github.com/fastapi/fastapi/releases/tag/0.165.0)**（FastAPI Releases，11-18）

  这次的功能只有一条：可配置的表单解析上限（PR #16784），用参数限制表单字段数量、单个字段大小这类维度，直接对应「一个超大 multipart 请求把 worker 内存打满」的老问题。发布说明开头更值得注意的是另一件事：FastAPI 现在带一个官方 skill，用 `uvx library-skills` 装进项目，作用是让编码 agent 按你实际安装的版本使用新特性与推荐写法，而不是凭训练数据猜 API。

  两件事指向同一个方向：框架开始把「防止被滥用」和「让 agent 正确使用自己」当成发布物的一部分。前者是配置项，后者是版本化文档的另一种形态——如果你的项目还在让 agent 自由发挥，这类 skill 比提示词里的「请参考官方文档」要可靠。
