## 今日概览

截至今天 10:30（UTC+8），过去 48 小时最值得关注的是两件性质相反的事：Anthropic 上市第五个交易日跌破 83 美元发行价，把「AI 公司估值」这件事第一次交给公开市场定价；OpenAI 数学团队则在同一天提交预印本，证明矩阵乘法的指数下界也是 2.25，与已有的上界合起来，这个困扰算法界五十多年的常数被钉死在 9/4。

工程侧有两条实用信息。一篇 arXiv 论文用 850 万个带认证参考值的输入做测试，指出 PyTorch 的 KL 散度在近距离分布上大面积算错，连 sign 都会翻负，而「clamp 到 0」只是遮住了症状；另一条是 Pooya Parsa 的 unkernel 把 Linux 内核编译成 WebAssembly，让浏览器里跑带图形、音频和网络的完整 Linux 变成可交互的现实。

- **[Quad9 从 11 月 24 日起停止为法国用户提供 DNS 解析](https://quad9.net/news/blog/quad9-service-deactivation-in-france/)**（Quad9 官方博客，11-24）

  上午 9:00（巴黎时间）起，任何到达 Quad9 服务地址的法国来源查询都会被拒绝。起因是体育版权方 beIn 要求其封禁一批被指与盗版流媒体相关的域名，法院支持了该要求，Quad9 因不配合被罚款。Quad9 的立场是：递归 DNS 并不是阻断内容的有效手段（任何人几秒钟就能自建解析器），而一旦接受「按 geoIP 判断用户所在地并据此屏蔽」，就等于承认 DNS 可以作为内容审查的执行环节，之后会被要求扩展到更多域名乃至道德、宗教、政治类内容。

  技术上的坦白也值得记一笔：Quad9 承认用 geoIP 判断「是否法国用户」必然既不精确又双向出错——IP 地理位置本身不准，移动运营商跨境、企业 WAN 跨国、VPN 出口与被代理用户的实际所在地完全脱钩。它宁愿接受明显的过度/不足屏蔽，也不做定向域名过滤。这是它在德国索尼案胜诉之后的第二场同类诉讼。

  对开发者而言这是一个基础设施层面的风险样本：公共解析器正在变成政策执行点。依赖 9.9.9.9 的服务需要准备降级路径，自建或在多个解析器间做健康检查不再是洁癖。

- **[Granular.Build：把一支 AI agent 团队放进可视化工作台](https://www.producthunt.com/products/granular-build)**（Product Hunt，11-24，193 票）

  解决的问题是「同时跑多个 agent 时，上下文和文件会互相踩」。做法有两层：一是把项目目录变成「brain」——一组 Markdown 文件，记录使命、受众、决策和路线图，再渲染成可视化的脑图和看板，agent 按卡片取任务；二是「boss agent 招募 worker」，每个 worker 跑在自己的真实终端和自己的项目副本（git worktree）里，模型可以是 Claude、Codex、Gemini、DeepSeek、GLM 等，不绑定单一厂商。

  和常见方案的区别在于定位：终端和 IDE 是给工程师的驾驶舱，Codex/Claude Code 桌面端锁定自家模型且一次一个会话，Lovable/Replit/Bolt 则替你选栈并把代码放在它们服务器上。Granular 反过来——文件留在本机、密钥放加密 vault、可以接 1400+ 应用、按自己的托管发布。

  免费版给 2 个项目、每个 4 个会话；Pro 解除限制，价格在官网。它假设你自带 Claude/Codex/Gemini 订阅，所以没有新增模型账单。是否值得试：如果你已经在同时跑两三个编码 agent 并靠手工复制粘贴同步上下文，这套「项目 brain + worktree 隔离」的模型确实对应真实痛点；但它是本地桌面应用，团队协作和远程执行还在路线图上（作者说定时任务与远程构建是下一步）。做者背景值得一提：Omar（Glorify 创始人）用 Granular 本身构建了 Granular 的官网、宣传图和视频。

## AI 技术

- **[OpenAI 数学团队预印本：矩阵乘法的指数就是 9/4](https://github.com/openai/math/tree/main/preprints/The-matrix-multiplication-exponent-is-nine-fourths-November-24-2026)**（openai/math 仓库，11-24）

  一句话版本：此前已知上界是 2.25（有构造性算法，虽然完全不实用），这次补齐了下界 Ω(n^2.25)，两边夹住，ω = 9/4 成为确定值，而不是「介于 2 与 2.371 之间」的区间。上一代最好的上界大约是 2.371。

  证明思路据摘要与讨论转述是这样的：如果指数能更小，那么张量网络会被压缩到足以违反一个已知下界——「判断若干个独立列表之间是否有重复元素」至少要看每个元素一遍。也就是说，更快的矩阵乘法会让你在不看全数据的情况下判断重复，逻辑上不成立。讨论里有人追问是否构造性，答案基本是否定的：它证明的是「不可能更快」，而不是给出算法。

  需要说清的限制：这是预印本，未经同行评审，我读的是仓库目录与 HN 讨论、论文 PDF 两次抓取均超时，没有读全文。HN 上还有一条值得记的更正——最初提交的标题写作 O(n^2.25)，实际应为 Θ(n^2.25)，因为这是精确界而非上界。

  对工程实践有没有影响？短期内没有。这类结果的作用是收窄理论地平线：既然 ω 不可能小于 2.25，所有基于「再快一点就能改变可行性」的架构假设都可以停止等待。这也解释了同一天 HN 上为什么有人问「这套技术能否变成真实的 GPU kernel」——答案在论文给出的范围内是不能。

- **[OpenAI 发布 GPT-6 蛋白质设计预印本：通用模型首次在对接任务上超过专用工具](https://openai.com/index/gpt-6-models-demonstrate-intrinsic-protein-design-capabilities/)**（OpenAI，11-24）

  核心主张是「内在能力」：只用推理加通用编程工具，不调用任何生物学专用模型，就能设计新的蛋白质结构和序列。测试覆盖 14 项任务，包括 minibinder 设计、motif scaffolding、CATH 折叠设计、结构预测、小分子对接、抗体-靶点结合预测、突变效应排序，并与合作伙伴 Onava 做了湿实验验证。

  真正有说服力的是几个具体数字。小分子对接（PoseBusters）GPT-6.2 拿到 93%，内部模型 96%，DiffDock-L 只有 50%；motif scaffolding 内部模型 43.7% 对 RFdiffusion 的 27.8%。湿实验里，为已知结构设计新序列的命中率在 MDM2 上是 75/88（85%），VEGF-A 是 26/42（62%），PD-1 只有 8/59（14%）；针对 5 个靶点的 322 个 minibinder 中，35 个（10.9%）呈结合阳性。

  被压住的部分同样重要。从序列预测结构这项，内部模型 TM-score 只有 0.38，ESMFold2 是 0.93——差得很远。整个流程仍然依赖 Boltz-2、OpenDDE、ESMFold2 这些专用模型来筛候选，论文自己承认尚不能证明可以零样本端到端独立生成。也就是说，这不是「通用模型替代领域模型」，而是「通用模型接管了设计与探索这一段，筛选仍靠专用模型」。另外，成果基于未发布的内部模型，文章没有给出任何对外访问时间表。

- **[Simon Willison：十二个月里的三个 LLM 拐点](https://simonwillison.net/2026/Nov/24/llm-inflection-points/)**（Simon Willison，11-24）

  这是他 AI Engineer Code Summit 主题演讲的文字版，把过去一年分成三段。第一段是 2025 年 11 月 24 日的 Claude Opus 4.5（恰好一年前）与同期的 GPT-5.1 系列：编码 agent 从「需要不停纠正」变成「默认结果基本正确」，这是他从「偶尔用」转向日常依赖的分界。第二段是今年 6 月的「Fable 类模型」——他给的定义很干脆：只要你能定义目标并提供必要工具，它们就能用暴力把问题解掉；例子是给模型五个 WebAudio 麦克风的访问权限，它把房间里烦人的蜂鸣声三角定位到 40 厘米以内。第三段是 9 月到 10 月在 3D 建模和游戏上的跃迁：他让 Opus 5.5（9 月 22 日发布）「把这个游戏做得有趣得多」，模型花了 12 小时自己试玩、加功能、重平衡，把一个无聊的 RTS 改成能持续玩下去的东西。

  需要标明测试条件：这是一位资深开发者基于自己日常工作的观察，不是基准测试，也不是可复现实验。「理解什么叫好玩」这种判断尤其如此，它可能只对特定模型版本、特定任务类型成立。

- **[LoomFormer：让 Transformer 在每个 token 上重新布线](https://huggingface.co/papers/2611.30634)**（Hugging Face Daily Papers，今日榜首 26 赞；[代码](https://github.com/Caiyun-AI/LoomFormer)，Apache-2.0）

  核心是 loom attention：把一个 head 的「垂直注意力」（对更早 head 的输出做注意力，来得到自己的 Q、K、V）和「水平注意力」（对 token 做注意力）交织起来，于是每个 token 都能重新安排自己的计算路径，而不是全程共用一套固定的连接。垂直注意力用归一化加门控的线性注意力实现在一份 per-token 矩阵记忆上，这份记忆同时充当第二条残差流，最终得到一个双流结构——向量流负责控制，矩阵流负责内容。

  训练数据值得记：同样 300B token、只多 2% FLOPs 的情况下，LoomPythia-2.8B 在下游任务上的平均增益约为 mHC-Pythia-2.8B 的 1.6 倍，零样本追平、五样本超过 Pythia-12B。作者称它匹配了用 3 倍以上算力训练的 Transformer，以及 HC/mHC、MUDDFormer、AttnRes 这些近期残差流基线（它们用了 1.7 到 2.8 倍算力）。

  限制要说在前面：论文与代码都是 11-23 才放出来，仓库目前 1 星、没有 description，所有对比都在作者自己的训练设置下，尚无独立复现。对做应用的人，它的价值不是马上换个 backbone，而是「第二条残差流 + 每 token 重连」这个结构直觉——它把「深度」从固定层数变成了可调用的记忆带宽。

- **[arXiv：KL 散度永不为负——除了在 PyTorch 里](https://arxiv.org/abs/2611.30835)**（arXiv 2611.30835，11-24）

  负的 KL 散度在数学上不可能，但 PyTorch 用户报告了多年，标准建议是 `clamp(min=0)`。这篇论文说，符号只是可见的那部分，真正的失败是静默的精度崩塌。作者用 850 万个带认证参考值的输入，覆盖 18 个闭式 KL 族和 `F.kl_div`，在 CPU 与 GPU 上都发现广泛的值与梯度错误：在 KL 约为 1e-7 附近，FP32 下超过 85% 的值相对误差至少 1%（FP16 对应 1e-3），散度更小时约 30% 直接变成负数。

  最反直觉的结论是「加精度没用」：把同样的公式放到高一档精度上评估，23 种配置里仍有 22 种存在 7%–51% 的显著错误。有效的是算法层面的改动——稳定的闭式分解、补偿求和，以及解析梯度，能消掉 97% 以上的显著误差；严格修复后，720 万个样例与 5.67 亿个 `F.kl_div` 分量全部正确舍入。

  为什么值得一个前端/全栈出身的人注意：只要你在做 embedding 相似度、蒸馏损失、VAE/RAG 打分这类「比较两个相近分布」的事，就可能踩在这个区间里，而错误不会报错、只会让训练悄悄变差。实用的动作是升级到包含修复的版本，或在近距离比较时改用论文给的稳定形式，不要靠 clamp 掩盖。

- **[songe：用你闲置的算力，在本地训练自己的模型](https://github.com/sous-labs/songe)**（GitHub，11-24 登上 HN 186 分；Apache-2.0）

  思路是把「训练」塞进日常使用的缝隙里。你照常用 opencode、pi 或任何兼容 OpenAI 接口的工具调用本地模型；Songe 在旁边观察每次动作之后发生了什么——工具返回了什么、报了什么错、你下一句说了什么。当 agent 空闲时，它拿这些轨迹去教模型预测这些结果。新版本只有在通过自检后才会被启用，数据全程不出本机。

  它对应的是一个真实缺口：现在的「个性化」基本靠上下文窗口和记忆文件，模型权重本身不变；而微调的门槛是标注数据和 GPU 时间。Songe 把标注这件事变成了「你正常工作时自然产生的反馈」，这是数据飞轮里最贵的一环。安装是 `pip install songe`。

  限制要说清楚：项目 11-20 才创建，不到一周，697 星，仍是早期；本地训练会持续占用机器，用「闲置算力」是理想描述，实际体验取决于你的机器和模型规模。判断标准应该是有没有可重复的评测，而不是 demo 里哪句话变顺了。

- **[Pinterest 用 4B 模型替换多阶段聚类，但最大提速来自「少推理」](https://www.infoq.cn/article/vaEUVvWD9AIaFXZhzSMH)**（InfoQ 中文，11-24；[原文](https://medium.com/pinterest-engineering/from-activity-to-intent-generating-user-journeys-with-llms-9652b9417626)）

  背景是「用户旅程」推断：把一个正在装修厨房的人分散在搜索橱柜、收藏台面、看防溅板瓷砖里的行为，合成一个连贯意图，而不是三个不相关的兴趣标签。旧系统是关键词 → embedding → 层次聚类 → 给簇命名 → 再排序，问题是会把相关行为拆散、标签笼统、把偶然点击误判成持续意图。

  新系统把这件事当成生成任务：微调后的 4B 模型读入 360 天内最多 150 条行为的时间序列加一份轻量画像，直接输出按优先级排序的旅程名。搜索与保存的权重高于偶然点击；大量原本在流水线里做的排序和过滤被挪进 prompt，包括「证据不足时允许返回空结果」。训练数据用前沿模型合成，再通过 SFT + LoRA 灌进开放权重的 Qwen3；他们试了 6 亿到 80 亿参数，选 4B 是为了质量和吞吐的平衡。

  线上效果：美加 A/B 测试里邮件点击率 +1.1%、推送打开率 +1.3%。但工程上最值钱的一条是——吞吐提升最大的一项措施是「不做推理」：系统记录每个用户旅程上次生成的时间，几天内处理过的人直接跳过。模型侧则用 vLLM + NVIDIA Dynamo、连续批处理、PagedAttention 和前缀缓存感知路由。

  这套组合值得抄的地方在于顺序：先想清楚哪些请求根本不必发，再谈推理优化。很多 agent 应用的成本问题，本质是重复计算。

- **[CUA-SEE：让 agent 的评测环境跟着 agent 一起进化](https://arxiv.org/abs/2611.30962)**（arXiv 2611.30962，11-25；通义 MAI；[HF 条目](https://huggingface.co/papers/2611.30962)）

  指出的问题很准：computer-use agent 一年内进步很快，评测却基本是静态的——难度天花板固定、功能覆盖有限、最后只给一个总分。结果是基准的判别力和诊断力随时间一起衰减，分数涨了也说不清是能力涨了还是题太旧。

  做法是一个闭环环境：任务和可执行验证器都从 rollout 的证据里共同长出来，并拆成三个独立目标。benchmark evolution 负责扩面，用同批 agent 校准难度、增长覆盖；diagnostic evolution 负责提分辨率，针对某个具体 agent 去探它的能力边界；verifier evolution 负责提精度，把变化的需求翻译成基于状态的检查点，再做对抗性验证。作者把这件事定位为「自我进化 agent 的可扩展对照物」——agent 在自进化，考题也得一起进化。

  对做 agent 产品的人，这条最可直接拿走的是观念：评测集不是一次性资产，它会随时间腐烂，需要像代码一样被维护和生成。限制是摘要没给具体数字——测了多少 agent、多少个应用、多少轮，以及提升幅度都不在摘要里，正文我未读到，因此这里不引用任何效果数据。

## 大前端与后端

- **[unkernel：把 Linux 内核编译成 WebAssembly，浏览器里跑图形程序](https://unkernel.dev)**（unkernel.dev，11-19 发布；[实测文章](https://fzakaria.com/2026/11/23/2035-came-early)，11-23）

  做法是把内核本身编译成 WASM（`unkernel-smp.wasm` 约 10.2 MiB，支持 SMP），只有用户态程序仍走模拟。这条分界线很关键：内核工作——启动、调度、系统调用——通常正是首次运行最慢的部分，把它跑在 wasm 速度上之后，Farid Zakaria 在 trynix.dev 上实测比 qemu-wasm 快 2 到 32 倍，具体倍数取决于负载。

  更值得注意的是外设是怎么接进去的：程序的 Wayland surface 由 wland 在页面里合成，浮在启动它的终端之上；VM 里带一个只有 virgl 驱动的精简 Mesa，编译成 WASM 后走浏览器的 WebGL2 渲染；虚拟 ALSA 声卡把音频接到页面；每个 TCP 连接开一条 WebSocket 到 Wisp 中继，所以 `curl`、`git clone`、`pip install` 都能用。作者最后在 Firefox 里启动 Linux（WASM）再启动 Firefox、再在里面加载同一个站点，花了四个多小时，内层要关 JIT、中层无 GL、外层得换本机中继。

  作者是 Pooya Parsa（Nuxt 作者，11-19 发布）。这条对前端工程师的意义在于它把「浏览器是操作系统」从比喻变成了可点开的链接——三百多万个 Nix 包版本可以直接在标签页里跑。当然，四个小时的 Firefox 套娃也说明性能边界还在，短期它是演示和教学工具，不是部署方案。

- **[Stalwart 1.2.0 成为 Exchange 的直接替代品](https://stalw.art/blog/microsoft-exchange-replacement/)**（Stalwart 官方博客，11-23）

  一句话：迁完邮箱、改完 DNS，客户端不用换——Outlook、Apple Mail、手机自带邮件 App 照常连。实现覆盖四套协议，且全部与 JMAP、WebUI 共用同一个 HTTPS 端口：MAPI over HTTP（EMSMDB 与 NSPI，支持缓存与在线模式）、EWS（Exchange 2010 SP2 至 2016 的 schema 版本）、Exchange ActiveSync（14.1 与 16.1）、以及 POX/SOAP/JSON 三种方言的 Autodiscover。

  兼容代码约 20 万行，工程上处理得很克制：独立 crate、单一 `exchange` feature 控制，不带该 feature 编译则代码不进二进制；即使官方构建里也默认禁用，禁用时服务器行为就像没这个功能；Exchange 专有属性只写进 JMAP Object Metadata，从未被 Exchange 客户端打开的账户不携带任何 Exchange 数据，删元数据即可清干净。协议支持在 AGPL 社区版里，不另收费。

  不支持的清单同样重要：公用文件夹、存档邮箱、MDM、RPC over HTTP，以及 NTLM 和 Kerberos——客户端只能用密码、App 密码或 OAuth。新版 Outlook 完全不可用，而且不只是不支持 Stalwart：即使它支持 IMAP，也会把服务器地址和凭据发给微软云代为连接，这对自托管等于失去意义；手机端 Outlook 同理。配套迁移工具 Vandelay 支持从本地 Exchange（EWS）和 Microsoft 365（Graph，含 OneDrive 文件）两侧导入。

  时机不难理解：Exchange 2016/2019 已于 2025-10-14 结束支持，EWS 在 Exchange Online 里 2026 年 10 月开始停用、2027 年 4 月移除，自托管路线只剩 Exchange SE 一条。作者把这件事定位成「桥」而不是方向。对需要数据主权的团队，这是目前少数不用换客户端的选项。

- **[Mason：给 Postgres 换一个列存只读副本，同一条 SQL 快 81 倍](https://masondata.ai/)**（Show HN，11-24，86 分）

  定位很直接：替换你现有的 Postgres 只读副本，SQL 不变、结果不变，但分析型查询快得多。官网给的对照是 1000 万行的 `GROUP BY` 聚合——主库 15.7 秒，Mason 0.193 秒，两者返回同样的答案。实现方式是列存，因此它天然区分 OLTP 与 OLAP 两类负载，而不需要你改 schema 或加物化视图。

  为什么值得看：大多数团队的「报表把主库拖慢」问题，解法要么是加只读副本（行存，聚合仍然慢），要么是上独立数仓（要 ETL，数据有延迟）。「同一条 SQL、同一个答案、只换执行引擎」这个约束条件如果能守住，迁移成本比数仓低一个量级。

  限制同样明显：这是 Show HN 阶段的产品，我读到的页面只给了这一个对比数字，没有定价、延迟特性、写入同步方式和一致性保证的说明。选型时至少要问清复制延迟、大事务和 DDL 的行为，以及「同样的答案」在浮点、时区、排序规则这些边角上是否成立。
